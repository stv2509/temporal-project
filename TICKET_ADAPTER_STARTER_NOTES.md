### 1. Где вообще должен жить `TicketAdapter`

Важно: **`TicketAdapter` — это не обязательно код внутри Django.**  
Это просто *абстракция* (интерфейс), которая может жить:

- в самом `starter.py` (как отдельный класс),
- или в отдельном модуле/пакете, которым пользуется starter‑сервис.

Тогда картинка такая:

- **Starter‑сервис (`starter.py` / Service A)**  
  - знает про тикетницу → реализует `TicketAdapterXxx` под конкретное API,
  - опрашивает/читает тикеты,
  - вызывает Temporal (`start_workflow`),
  - ходит в Django по HTTP, чтобы создавать/обновлять `Request`.
- **Django**  
  - ничего не знает о тикетнице,
  - даёт REST‑интерфейс для `Request` (list/detail/run/update_status и т.д.),
  - выступает «витриной» и единым хранилищем заявок.
- **Temporal‑workflow + worker**  
  - ничего не знают ни о тикетнице, ни о starter’е,
  - работают только с `ticket_id` и данными из `Request` через backend API.

То есть `TicketAdapter` — это *деталь реализации внутри starter‑сервиса*, а не «штука, пришитая к Django».

### 2. Почему вариант B (отдельный starter‑сервис) хорошо сочетается с `TicketAdapter`

Описанный вариант B на самом деле уже подразумевает ровно это:

- starter ходит **напрямую** в тикетницу → это и есть место для `TicketAdapter`.
- starter вызывает Temporal и Django → он единственная точка, где надо будет менять код при смене тикетницы.
- Django остаётся максимально нейтральным: с ним общаются и текущий starter, и потом новый (под другую тикетницу) — API Django не меняется.

Перенос в отдельный скрипт/сервис проходит так:

- Сейчас: `starter.py` (скрипт) содержит:
  - код подключения к тикетнице (`TicketAdapterCurrent`),
  - код вызова Temporal,
  - код вызова Django.
- Потом: делаешь из этого **сервис** (FastAPI / простой daemon), но:
  - интерфейс `TicketAdapter` и логика вокруг него остаются,
  - добавляется только «обвязка» (долгоживущий процесс, healthcheck и т.п.).

Ничего в Django и в workflow’ах при этом трогать не надо.

### 3. Будут ли проблемы с переносом?

Если держать границы такими:

- **Workflow’ы** видят только: `ticket_id`, `normalized`, статусы через backend API.
- **Django** видит только: HTTP‑клиентов (starter, UI), не умеет ходить в тикетницу.
- **Starter** видит тикетницу через `TicketAdapter` и умеет говорить с Django и Temporal,

то:

- Смена тикетницы = написать новый `TicketAdapterNew` и, возможно, чуть поправить маппинг полей → всё внутри starter‑сервиса.
- Перенос `starter.py` из «скрипта» в «микросервис» = в основном инфраструктурная задача, бизнес‑код тот же.
- Никакой «жёсткой завязки на TicketAdapter» у Django и Temporal не будет: это внутренняя деталь слоя интеграции.

Если нужно, можно отдельно накидать конкретный набор методов для `TicketAdapter` и какие DTO он должен возвращать, чтобы будущая смена тикетницы была максимально безболезненной.
